# A/B-test platform

Сервис A/B-тестирования: детерминированное разделение пользователей по экспериментам, сбор событий и честная проверка статистической значимости результата — без ложной уверенности на недостаточных данных.

## Обзор

Владелец эксперимента (продакт/аналитик) хочет проверить гипотезу («вариант B работает лучше варианта A»), не полагаясь на угадывание. Сервис решает полный цикл: создание эксперимента → детерминированная выдача варианта пользователю → запись событий → расчёт конверсии и статистической значимости разницы между вариантами, с явными предупреждениями там, где данных недостаточно для надёжного вывода, а не тихим `null` или ложно значимым результатом.

## Особенности

* **Детерминированный бакетинг:** вариант для пользователя вычисляется хэшем (`sha256` от `user_id + experiment_id`), без хранения состояния — один и тот же пользователь всегда попадает в один и тот же вариант.
* **Автоматический выбор статтеста:** z-test или точный тест Фишера — в зависимости от объёма данных в группе (порог: `np < 5` или `n(1-p) < 5` → Фишер), чтобы не доверять нормальному приближению на малых выборках.
* **Honest null:** если данных недостаточно для вывода (нулевая конверсия контроля, слишком юный эксперимент, скошенный sample ratio) — сервис возвращает `status = "insufficient_data"` или `srm = null` с текстовым объяснением причины, а не пустое поле без контекста.
* **Поправка на множественные сравнения:** при нескольких тестовых вариантах — Бенджамини-Хохберга (FDR), с «семьёй» сравнений, корректно исключающей `insufficient_data` (см. REQ-10 в [spec.md](spec.md)).
* **Детектор sample ratio mismatch (опционально):** `?check_srm=true` — хи-квадрат тест на соответствие фактического распределения пользователей по вариантам заданным весам; строгий порог `p < 0.01`, так как ложное срабатывание здесь дороже обычной ошибки (недоверие к валидному в остальном эксперименту).
* **Оценка «сколько ещё ждать»:** если мощности пока не хватает, `/results` считает `estimated_days_needed` по собственному темпу набора каждого варианта (не усреднённому по эксперименту — иначе оценка искажается при неравном сплите трафика).

## API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/experiments` | Создать эксперимент (валидация: сумма весов = 100, минимум 2 варианта) |
| `GET` | `/experiments/{id}/variant?user_id=` | Получить вариант для пользователя (детерминированно) |
| `POST` | `/events` | Записать событие (например, `conversion`) |
| `GET` | `/experiments/{id}/results?check_srm=` | Конверсия по вариантам + статзначимость, опционально SRM-проверка |

Полный контракт с примерами запросов/ответов — в [spec.md](spec.md#3-контракт-api).

## Быстрый старт

```bash
make install   # python3 -m pip install -r requirements.txt
make test      # полный набор тестов (без perf-теста)
make run       # запустить локально (uvicorn, --reload)
```

Swagger-документация после `make run` — на `/docs`.

## Как это проверяется

29 тестов: 28 в `make test`, плюс отдельный нагрузочный тест (`make test-perf`, не входит в обычный прогон, чтобы не делать его медленным/нестабильным на разном железе). Статистические формулы сверяются с эталонными библиотеками — `scipy.stats.proportions_ztest`, `scipy.stats.fisher_exact`, `statsmodels.stats.multitest.multipletests` — с точностью до 0.001, а не просто «не падает».

Каждое поведение формализовано как EARS-требование (REQ-1…14, шаблоны Ubiquitous / Event-driven / Unwanted behavior / Optional feature) с Гёркин-критериями приёмки в [spec.md §3.2](spec.md), и для решений с нетривиальным обоснованием — отдельные ADR в [docs/adr/](docs/adr/) (например, почему доверительный интервал всегда считается по Wald, даже когда для p-value выбран Фишер).
