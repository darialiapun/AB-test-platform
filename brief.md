# Бриф: статистическая значимость результатов эксперимента

*Один сценарий использования AB Lab — не весь продукт целиком, как учили на занятии 3 (Intent engineering).*

## Пользователь

Владелец эксперимента (продакт/аналитик), который уже собрал данные по A/B-тесту через существующий MVP: создал эксперимент, пользователи получили варианты через `/variant`, события записаны через `/events`. Теперь он хочет понять, можно ли доверять разнице в конверсии между вариантами — или это может быть случайность.

## Проблема

Сейчас `/results` показывает только сырые цифры (конверсия по каждому варианту), и по ним невозможно понять, реальна ли разница или это шум. Из-за этого легко сделать неверный вывод: внедрить вариант, который на самом деле не лучше, или отказаться от варианта, который на самом деле работает.

## Основной сценарий

1. Владелец эксперимента запрашивает `GET /experiments/{id}/results`.
2. Сервис проверяет, достаточно ли накоплено данных для надёжного вывода (по расчёту необходимого объёма выборки). Если недостаточно — возвращает предупреждение с оценкой, сколько ещё нужно данных/дней, не блокируя при этом сырые цифры.
3. Если данных достаточно, сервис для каждого тестового варианта сравнивает его с контролем: автоматически выбирает z-test или точный тест Фишера (в зависимости от объёма данных в группе), считает p-value и 95%-й доверительный интервал разницы конверсий.
4. Если тестовых вариантов для сравнения больше одного, применяет поправку Бенджамини-Хохберга (FDR) на множественные сравнения.
5. Владелец видит по каждому сравнению: p-value, значим ли эффект (да/нет), доверительный интервал. Если конверсия в каком-то варианте равна нулю — дополнительное предупреждение о возможной технической проблеме в этом варианте.

## Границы

**В работе:**
- сравнение каждого тестового варианта только с контролем (не все варианты между собой)
- двусторонний тест
- фиксированный alpha = 0.05 (95% доверительный интервал)
- автоматический выбор между z-test и точным тестом Фишера по объёму данных в группе (порог: np < 5 или n(1-p) < 5 → Фишер)
- поправка Бенджамини-Хохберга (FDR) при нескольких сравнениях одновременно
- предупреждение о недостаточном объёме данных, с оценкой "сколько ещё нужно"
- предупреждение при нулевой конверсии в варианте (результат всё равно считается)
- ответ `/results` быстрее 2–3 секунд при объёме до 50 000 событий

**Не в работе (сознательно откладываем):**
- расчёт значимости для непрерывных метрик (средний чек, время на сайте и т.п.) — только конверсия
- визуализация и графики — только JSON-ответ API, фронтенда пока нет
- автоматический подбор нужных метрик под конкретный запрос (из пула 35 метрик) — отдельная будущая задача
- бутстреп-метод
- адаптивный (не фиксированный) расчёт alpha

## Нефункциональные требования

- `GET /experiments/{id}/results` отвечает быстрее 2–3 секунд при объёме эксперимента до 50 000 событий
- расчёт детерминирован: одинаковые входные данные → всегда одинаковый результат

## Критерии успеха (проверяется автотестами)

- p-value z-test совпадает с `scipy.stats.proportions_ztest` с точностью до 0.001 на одинаковых входных данных
- p-value точного теста Фишера совпадает с `scipy.stats.fisher_exact` с точностью до 0.001
- сервис автоматически переключается на тест Фишера, когда объём в группе меньше порога — проверяется тестом на заведомо маленькой выборке (например 3 из 5 и 2 из 5)
- скорректированные p-value (Benjamini-Hochberg) совпадают с `statsmodels.stats.multitest.multipletests(method="fdr_bh")` с точностью до 0.001
- эксперимент с заведомо недостаточным объёмом данных (ниже расчётного порога мощности) возвращает предупреждение, а не ложно уверенный результат
- вариант с 0 конверсиями не вызывает ошибку (деление на ноль и т.п.), а возвращает корректный 0% и предупреждение

## Негативные сценарии

- в одном из вариантов 0 конверсий → результат считается, но добавляется предупреждение о возможной технической проблеме
- в эксперименте только один вариант (второй не создан) → `/results` возвращает ошибку с понятным сообщением вместо попытки сравнения
- данных пока недостаточно для надёжного вывода → возвращается предупреждение с оценкой необходимого объёма, а не "пустой" или ложно значимый результат
