# A/B-платформа — спецификация

## 1. Обзор

**Проблема.** Владелец продукта хочет проверить гипотезу («вариант B работает лучше варианта A»), не полагаясь на угадывание, и получить честный ответ: разница реальна или это случайность.

**Пользователь.** Один тип: владелец эксперимента (продакт/аналитик, который запускает A/B-тест на своём продукте).

**Основной сценарий (сквозной, от начала до конца):**
1. Владелец создаёт эксперимент: название, варианты, доля трафика на каждый.
2. Продукт (в демо-версии — скрипт-имитатор) запрашивает у платформы вариант для конкретного пользователя.
3. Продукт присылает платформе события (например, «пользователь совершил целевое действие»).
4. Владелец смотрит результаты: сколько пользователей в каждой группе, конверсия, есть ли статистически значимая разница.

## 2. Границы МВП и полной версии

| Что | МВП (к следующей паре) | Полная версия (курсовая сдача) |
|---|---|---|

## 3. Контракт API

### `POST /experiments`
Создать эксперимент.
```json
// запрос
{
  "name": "button_color",
  "variants": [
    {"name": "control", "weight": 50},
    {"name": "treatment", "weight": 50}
  ]
}
// ответ 201
{"id": "exp_1", "name": "button_color", "variants": [...], "status": "running"}
```
Правило: сумма `weight` по вариантам должна быть равна 100, иначе 400.

### `GET /experiments/{id}/variant?user_id={user_id}`
Получить вариант для пользователя.
```json
// ответ 200
{"experiment_id": "exp_1", "user_id": "u42", "variant": "control"}
```
**Гарантия:** при любом количестве повторных вызовов с тем же `user_id` и `experiment_id` возвращается один и тот же `variant`.

### `POST /events`
Записать событие.
```json
// запрос
{"experiment_id": "exp_1", "user_id": "u42", "event_type": "conversion"}
// ответ 201
{"status": "recorded"}
```

### `GET /experiments/{id}/results`
Получить результаты.
```json
// ответ 200 (МВП)
{
  "variants": [
    {"name": "control", "users": 512, "conversions": 40, "conversion_rate": 0.078},
    {"name": "treatment", "users": 498, "conversions": 61, "conversion_rate": 0.122}
  ]
}
// ответ 200 (полная версия, добавляется значимость)
{
  "variants": [...],
  "significance": {"p_value": 0.031, "significant": true, "method": "two-proportion z-test"}
}
```

### 3.1 Контракт значимости (полная версия, детали поведения)

- **Контроль определяется позиционно**: контроль — первый вариант в списке `variants`, в порядке, в котором он был передан в `POST /experiments` при создании. Имя `"control"` не зарезервировано и не проверяется — ответственность за порядок несёт вызывающая сторона.
- Каждый тестовый (не первый) вариант сравнивается только с контролем; результаты сравнений возвращаются в том же порядке, в котором варианты были созданы.
- **Доверительный интервал всегда считается по формуле Wald**, независимо от того, какой тест выбран для p-value (z-test или точный тест Фишера). Это осознанное ограничение v1: для малых выборок, где выбирается Фишер именно из-за того, что нормальное приближение ненадёжно, Wald CI — то же приближение, с типичными проблемами покрытия у границ 0%/100%. Переход на Wilson/Clopper-Pearson для этого случая в v1 не делается.
- Если конверсия варианта равна 0%, в ответ добавляется предупреждение вида: `Variant '<name>' has 0% conversions out of <N> users. This may be a real result or a tracking/integration problem - it does not by itself indicate which.` Предупреждение называет факт и обе возможные причины, не утверждая, что это техническая проблема.
- Если необходимый объём выборки невозможно оценить (у контроля пока 0 пользователей, либо 0 наблюдённых конверсий при любом количестве пользователей — целевой эффект не определён), статус сравнения — `insufficient_data` без числовой оценки, и в `warnings` добавляется объяснение причины: `Cannot estimate the required sample size yet: the control variant has no observed users yet` (или `has 0 observed conversions`) `, so the target effect size is undefined.`
- Скорость накопления пользователей для оценки `estimated_days_needed` считается **отдельно для каждого варианта** (его собственные users / прошедшие с создания эксперимента дни), а не усреднённо по эксперименту — иначе оценка искажается при неравном сплите трафика между вариантами.
- Если `estimated_days_needed` не может быть посчитан, потому что темп набора отстающей группы (или обеих) пока не измерим (эксперимент слишком молод, либо в группе 0 пользователей), поле остаётся `null`, но в `warnings` добавляется объяснение причины: `Cannot estimate days needed yet: enrollment rate for '<name>' is not yet measurable (too new, or no users observed yet).` — тот же принцип, что и для необъяснённого `required_users_per_group = null`: `null` никогда не остаётся без текстового объяснения.
- **Определение "семьи" для поправки Бенджамини-Хохберга**: `m` (число сравнений, участвующих в поправке) равно числу сравнений со статусом `ok` (то есть у которых есть p-value) в данном ответе `/results`. Сравнения со статусом `insufficient_data` не входят в `m` и не участвуют в поправке — они не являются выполненными тестами, поэтому не должны ни усиливать, ни ослаблять коррекцию для тех сравнений, у которых p-value действительно посчитан. Если тестовых вариантов несколько и у всех разный статус, `m` = количество именно `ok`-сравнений, а не общее число тестовых вариантов.
- **Пересечение `zero_conversion_warnings` и `comparisons[i].warnings` — осознанное, не дефект.** Оба могут одновременно описывать один и тот же факт (например, 0 конверсий у контроля) разными словами, потому что у них разная роль: `zero_conversion_warnings` — общий флаг качества данных по конкретному варианту (не привязан к тому, с кем он сравнивается), а `warnings` внутри сравнения — объяснение, почему именно этот расчёт пришлось скорректировать или пропустить. Эти поля не связаны между собой (нет общего кода/id) и не объединяются в один текст.

### 3.2 Формальные требования (EARS + Дано/Когда/Тогда)

Каждое требование ниже — формализация одного из пунктов 3.1. "Проверяется" честно отражает текущее покрытие тестами на момент записи этого раздела: где покрытия нет или оно частичное, это сказано прямо, а не домыслено.

#### Ubiquitous

**REQ-1.** Сервис SHALL считать контролем первый вариант в списке `variants`, переданном в `POST /experiments` при создании эксперимента.
- Дано: эксперимент создан с вариантами в порядке [V1, V2, …, Vn], где V1 не обязательно назван `"control"`.
- Когда: запрошены `GET /experiments/{id}/results`.
- Тогда: во всех элементах `comparisons[]` поле `control` равно имени V1, независимо от алфавитного порядка имён или объёма данных у каждого варианта.
- Проверяется: `test_variant_order_is_creation_order_not_alphabetical_or_by_volume`.

**REQ-2.** Сервис SHALL использовать relative MDE = 10% и power = 0.80 при расчёте необходимого объёма выборки (`required_sample_size_per_group`).
- Дано: базовая конверсия контроля равна X, где X > 0.
- Когда: вызван `required_sample_size_per_group(X)` любое количество раз.
- Тогда: результат — одно и то же целое число при каждом вызове, рассчитанное по формуле мощности с relative MDE=10%, power=0.80, alpha=0.05.
- Проверяется: `test_required_sample_size_is_deterministic` (детерминированность), `test_required_sample_size_none_when_baseline_zero` (случай X=0), `test_required_sample_size_uses_10_percent_relative_mde_and_80_percent_power` (независимая реконструкция формулы из `scipy.stats.norm`, фиксирует именно значения 10%/0.80 — не через `statsmodels.stats.power`, так как его effect-size параметризация иная (Cohen's h) и не эквивалентна формуле здесь).

**REQ-3.** Сервис SHALL всегда вычислять `confidence_interval` по формуле Wald, независимо от того, какой тест (z-test или Фишер) выбран для p-value.
- Дано: сравнение варианта с контролем, где объём данных мал и для p-value выбран точный тест Фишера.
- Когда: рассчитывается `confidence_interval` для этого сравнения.
- Тогда: границы интервала вычислены по формуле Wald (`wald_confidence_interval`), той же, что и при z-test — не Wilson, не Clopper-Pearson.
- Проверяется: `test_confidence_interval_is_wald_even_when_fisher_is_selected` — сверяет CI, возвращённый через `compute_significance` в сценарии, где выбран Фишер, с `wald_confidence_interval`, вызванной независимо на тех же входных данных. См. ADR 0001.

**REQ-4.** Сервис SHALL вычислять скорость накопления пользователей (`rate_per_day`) отдельно для каждого варианта (его users / дни с момента создания эксперимента), а не усреднённо по эксперименту.
- Дано: эксперимент с неравным сплитом трафика и/или неравным накопленным количеством пользователей у контроля и у тестового варианта.
- Когда: рассчитан `estimated_days_needed`.
- Тогда: оценка использует собственную скорость набора отстающей группы, а не общую скорость по эксперименту.
- Проверяется: `test_estimated_days_uses_each_variants_own_rate_not_averaged` — асимметричный сценарий (control 10x больше users, чем treatment), где усреднённая реализация дала бы другое число; тест явно сверяет результат с "неправильным" (усреднённым) вариантом и показывает, что он не совпадает.

**REQ-9** *(нумерация продолжает Q8 для сквозной прослеживаемости)*. Сервис SHALL возвращать `p_value`, `adjusted_p_value`, `confidence_interval` и `conversion_rate` без округления на уровне API.
- Дано: любой расчёт значимости.
- Когда: сформирован JSON-ответ `/results`.
- Тогда: числовые поля содержат полную точность float, без принудительного округления до фиксированного числа знаков.
- Проверяется: отсутствием кода округления в `app/significance.py`/`app/schemas.py`. Отдельный тест не предлагается — тест на "отсутствие округления" проверял бы отсутствие кода, а не поведение.

**REQ-10.** Сервис SHALL считать `m` (размер семьи) для поправки Бенджамини-Хохберга равным числу сравнений со статусом `ok` в текущем ответе `/results`, исключая сравнения со статусом `insufficient_data`.
- Дано: эксперимент с несколькими тестовыми вариантами, у части из которых достаточно данных (`ok`), у части — недостаточно (`insufficient_data`).
- Когда: запрошены `/results`.
- Тогда: `adjusted_p_value` каждого `ok`-сравнения рассчитан с `m`, равным числу именно `ok`-сравнений, а `insufficient_data`-сравнения не влияют на эту поправку.
- Проверяется: `test_bh_family_excludes_insufficient_data_comparisons`, `test_multiple_treatments_get_bh_correction`.

#### Event-driven

**REQ-11.** WHEN вызван `GET /experiments/{id}/results` при объёме эксперимента до 50 000 событий, сервис SHALL вернуть ответ быстрее 5 секунд.
- Дано: эксперимент с объёмом данных до 50 000 событий.
- Когда: выполнен `GET /experiments/{id}/results`.
- Тогда: время ответа меньше 5 секунд.
- Проверяется: `tests/test_performance.py::test_results_endpoint_under_budget_for_50k_events` (запускается отдельно через `make test-perf`, не входит в `make test`).

#### Unwanted behavior

**REQ-5.** IF конверсия варианта равна 0% при users > 0, THEN сервис SHALL добавить в `zero_conversion_warnings` предупреждение, называющее факт и обе возможные причины (реальный результат или проблема сбора данных), без утверждения, что это техническая проблема.
- Дано: вариант с users > 0 и conversions = 0.
- Когда: запрошены `/results`.
- Тогда: `zero_conversion_warnings` содержит запись с `variant` = имя этого варианта и текстом, упоминающим обе возможные причины, а не только "possible tracking problem".
- Проверяется: `test_zero_conversion_variant_does_not_crash_and_warns` — проверяет наличие записи для нужного варианта И точный текст (обе причины присутствуют, старая формулировка "possible tracking problem" отсутствует).

**REQ-6.** IF базовая конверсия контроля не определена (у контроля 0 пользователей, либо 0 наблюдённых конверсий при любом количестве пользователей), THEN сервис SHALL вернуть `status = "insufficient_data"` с `required_users_per_group = null` и добавить в `warnings` объяснение причины отсутствия оценки.
- Дано: у контроля 0 пользователей, ИЛИ у контроля есть пользователи, но 0 конверсий.
- Когда: запрошены `/results`.
- Тогда: соответствующее сравнение имеет `status = "insufficient_data"`, `required_users_per_group = null`, и `warnings` содержит объяснение (`"...has no observed users yet"` или `"...has 0 observed conversions"`), а не пустой список.
- Проверяется: `test_control_with_zero_users_warns_with_reason_not_silently` — именно ветка "у контроля 0 пользователей" (которая раньше возвращала `insufficient_data` с пустым `warnings`, до исправления в рамках этой сессии).

**REQ-7** *(ранее единственная строка в этом разделе)*. IF варианты эксперимента переданы в `POST /experiments` не в порядке «контроль первым», THEN сервис SHALL использовать первый переданный вариант как контрольный без уведомления об ошибке или предупреждения — порядок не проверяется и не валидируется.
- Дано: варианты переданы в порядке, где задуманный контроль не первый (например, `["treatment", "control"]`).
- Когда: вызван `POST /experiments`, затем `GET /results`.
- Тогда: статистическим контролем становится `"treatment"` (первый по порядку), без ошибки 4xx и без предупреждения о неожиданном порядке.
- Проверяется: тем же тестом, что REQ-1 — `test_variant_order_is_creation_order_not_alphabetical_or_by_volume` (создаёт `["zeta", "alpha"]` и показывает, что имя не влияет на выбор контроля).

**REQ-8.** IF темп набора отстающей группы (или обеих) не измерим (эксперимент слишком молод, либо в группе 0 пользователей), THEN сервис SHALL вернуть `estimated_days_needed = null` с объясняющим `warning`, называющим затронутый вариант(ы).
- Дано: у контроля и/или тестового варианта недостаточно данных, и темп набора отстающей группы нельзя измерить (возраст эксперимента меньше `MIN_ELAPSED_DAYS_FOR_RATE_ESTIMATE`, либо 0 пользователей).
- Когда: запрошены `/results`.
- Тогда: `estimated_days_needed = null`, и `warnings` содержит запись, упоминающую "enrollment rate" и имя затронутого варианта.
- Проверяется: `test_estimated_days_is_none_when_experiment_too_young_to_measure_rate`.

#### Пробелы по шаблонам (честно, без выдумывания)

- **State-driven** (`WHILE <состояние>, SHALL...`) и **Optional feature** (`WHERE <фича включена>, SHALL...`) — среди решений этой сессии нет ни одного естественного кандидата. Если такие требования появятся (например, поведение, зависящее от `status` эксперимента, или опциональный SRM-детектор из раздела 6), они должны быть добавлены сюда отдельно, а не задним числом притянуты к существующим пунктам.

## 4. Модель данных

- `experiments`: id, name, variants (json), created_at, status
- `assignments`: experiment_id, user_id, variant, assigned_at *(можно не хранить и пересчитывать хэшем каждый раз — обе схемы допустимы, но хранение даёт возможность аудита)*
- `events`: id, experiment_id, user_id, event_type, created_at

## 5. Алгоритм бакетинга

```
bucket = hash(user_id + ":" + experiment_id) % 100
вариант = тот, чей кумулятивный диапазон weight содержит bucket
```
Хэш детерминированный (например, md5 или sha256 от строки, взять первые байты как int). Одинаковый вход → всегда одинаковый выход, без необходимости синхронизации между серверами.

## 6. Что нужно доказать машиной (требование на оценку 10)

1. **Устойчивость бакетинга.** Тест: для фиксированного `(user_id, experiment_id)` вызвать `/variant` 100+ раз — все ответы совпадают. Дополнительно: для 10 000 разных `user_id` реальное распределение по вариантам совпадает с заданными `weight` с разумной погрешностью.
2. **Корректность статзначимости.** Тест: сгенерировать данные с известным сдвигом конверсии → результат функции значимости сравнивается с эталонным расчётом (например, `scipy.stats.proportions_ztest`) → должны совпадать в пределах точности.
3. *(бонус)* **Детектор SRM** (sample ratio mismatch). Тест: подложить данные, где фактическое разделение статистически отличается от заданного (например, реально 60/40 вместо 50/50) → детектор обязан это заметить (хи-квадрат тест на соответствие пропорций).

## 7. Скрипт-имитатор продукта

Отдельный скрипт `demo/simulate.py`:
- генерирует N «пользователей» (например, 5000)
- для каждого получает вариант через `/variant`
- «решает», совершил ли пользователь целевое действие, с разной вероятностью для разных вариантов (задаётся параметром — нужно для проверки, что тест значимости и ловит реальный эффект, и не ловит эффект там, где его нет)
- отправляет события через `/events`

Этот скрипт одновременно служит и демонстрацией работы платформы целиком, и источником данных для проверки корректности статистики.

## 8. Автоматические проверки (`make test`)

- тест детерминированности бакетинга
- тест на соответствие распределения заданным весам (статистически, с допуском)
- тест корректности расчёта конверсии
- *(после МВП)* тест корректности статзначимости против эталона
- *(бонус)* тест детектора SRM

**Perf-тест (`make test-perf`, не входит в `make test`).** Нефункциональное требование "`/results` быстрее 2–3 секунд при 50 000 событий" проверяется отдельным тестом (`tests/test_performance.py`, помечен `@pytest.mark.perf`), который не запускается в рамках обычного `make test` — он исключён через `pytest -m "not perf"`, чтобы не делать основной прогон медленным или нестабильным на разном железе. Порог в тесте — 5 секунд (с запасом над целевыми 2–3с), чтобы не ловить ложные падения.

## 9. Что сознательно не входит в МВП

Frontend-дашборд, реальный расчёт значимости, деплой, авторизация, защита от повторной отправки событий — всё это добавляется отдельными слоями после того, как базовый цикл работает и проходит тесты.
